# 기능 요청 분석하기

저장소 루트에서 `$analyze-request raidio-biz winter-new-channel-popup`처럼 호출한다. 첫 번째 값은 프로젝트 폴더명이고 두 번째 값은 기능 폴더명이다.

1. 두 값이 각각 영문 소문자와 숫자로 이루어진 단어를 하이픈으로 연결한 이름인지 확인한다. 값이 빠졌거나 형식이 맞지 않으면 호출 예시를 안내한다.
2. `projects/<프로젝트>/project.md`, `projects/<프로젝트>/features/<기능>/request.md`와 관련 기존 산출물을 읽는다. 프로젝트 문서나 요청서가 없으면 해당 경로를 알려준다. 요청서가 비어 있거나 양식만 있으면 작성이 필요한 항목을 안내하고 중단한다. 배경, 대상 사용자, 기대 결과가 불명확해 분석 방향이 달라질 수 있다면 먼저 핵심 질문을 한다.
3. 요청 범위에 맞춰 분석 분량을 정한다.

   - 변경 내용과 적용 위치가 명확하고 기존 사용자 흐름이나 정책에 영향이 없는 간단한 요청은 `analysis.md`에 **검토 요약**만 작성한다. 무엇을 바꾸는지와 변경 결과를 어떻게 확인할지를 적는다. 예를 들어 버튼 문구를 바꾸는 요청이라면 새 문구가 표시되고 버튼을 눌렀을 때 기존 목적지로 이동하는지 확인한다고 적는다.
   - 추가 분석이 필요하면 `templates/analysis.md`에 내용이 있는 경우 해당 형식을 참고한다. 템플릿이 비어 있거나 없으면 아래 항목을 참고해 판단에 필요한 내용만 작성한다.

   - **문제와 기대 결과** — 해결할 문제, 대상 사용자, 기대하는 변화를 정리한다.
   - **현재 흐름과 근거** — 사용자가 지금 어떻게 행동하는지 적고, 확인된 사실에 출처를 남긴다.
   - **원인 가설과 해결 방법** — 가설과 확인 방법을 적고, 요청한 해결 방법이 목적에 맞는지 검토한다. 필요하면 대안의 장단점도 비교한다.
   - **남은 질문** — 프로세스와 정책을 정하기 전에 확인할 내용을 적는다.

4. 분석을 같은 기능 폴더의 `analysis.md`에 저장한다. 기존 분석이 있다면 먼저 읽고, 사용자가 갱신을 요청한 경우 기존 결정과 근거를 보존하며 수정한다. 저장 경로와 다음 단계에 영향을 주는 미결 사항을 알려준다.
